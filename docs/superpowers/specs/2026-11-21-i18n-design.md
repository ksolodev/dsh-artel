# Full internationalization for dsh-artel

Date: 2026-11-21
Status: approved design, ready for implementation planning
Target release: 0.14.0

## 1. Summary

dsh-artel currently has a trilingual client UI (en/ru/zh), but the host emits
user-visible prose that the client renders verbatim: the feed is English, the
factory and queue journals are Russian. Language is whatever DSH chooses, with
no product-level switch, and adding a fourth language requires editing
`lib/client.js`.

This design turns all user-visible product text into structured keys resolved
from per-language JSON catalogs, adds a language setting stored per profile,
and makes a new language a data-only addition. Agent prompts, agent output,
command output, diffs, and repository paths remain untranslated.

## 2. Goals and non-goals

Goals:

- One language switch for the whole Artel surface: UI, feed, factory journal,
  queue journal and progress, error messages, plugin card metadata.
- Language selection independent of DSH, defaulting to the DSH language.
- Already persisted runs, tickets and events re-render in the selected
  language; no data migration.
- Adding a language is `locale/<tag>.json` plus one registry line, with no
  changes to host or client logic.
- Correct plural forms and date/number formatting for the selected language.
- CI-enforced catalog completeness and placeholder parity.

Non-goals:

- Translating agent prompts (`lib/prompts.js`), PR/commit text, branch names
  produced by agents, or any content the agent generates.
- Translating `ARCHITECTURE.md`, `CHANGELOG.md`, or `docs/publishing.md`.
- RTL layout implementation. `meta.dir` is reserved so a future language does
  not require a schema change.
- Server-side translation, runtime catalog fetching, or an external
  translation platform.

  `:549`, `:579`, `:620`, `:1256`, `:1359`; `lib/queue.js:76`, `:104`,

- `lib/client.js` is a classic script loaded through

- The project has no build step; `node --test test/*.test.js` is the test
  entry point.

## 4. Decisions

- **Approach A: keys in events plus a generated catalog.** Host events carry
  `key` and `params` next to an English `text`. The client resolves keys from
  a compiled-in catalog. This gives instant switching and re-rendering of
  history without HTTP catalog loading or server-side translation.
- **Catalog format:** one JSON file per language, `meta` for DSH plugin-card
  fields and `strings` for the product.
- **Generated module:** `tools/build-locales.mjs` compiles `locale/*.json`
  into a marked region of `lib/client.js`. The host does not import the
  catalog; it only emits keys.
- **Language storage:** `<stateDir>/settings.json`, per profile. Not
  localStorage, not cordis config.
- **Language selection:** explicit switch in the Artel surface header, default
  "as in DSH".
- **Docs scope:** `README` and the user guide are translated; architecture,
  changelog and release docs stay English.
- **Translation workflow:** owner plus external PRs, one JSON file per
  language; CI checks completeness.

## 5. Architecture

### 5.1 Locale catalog

`locale/<tag>.json`:

```json
{
  "meta": {
    "title": "Artel",
    "description": "Kanban factory for DSH agents",
    "detail": "docs/guide.md",
    "nativeName": "English",
    "dir": "ltr"
  },
  "strings": {
    "surface.title": "Artel",
    "queue.progress.auto": "Auto-queue running · {done} of {total}",
    "feed.copy.preparing": "Preparing a copy of {project}."
  }
}
```

Rules:

- `<tag>` is a BCP-47 tag matching
  `^[A-Za-z]{2,8}(-[A-Za-z0-9]{1,8})*$`; the filename stem is the language id.
- `meta.title`, `meta.description`, `meta.detail`, `meta.nativeName` are
  required and non-empty. `meta.dir` is optional, `ltr` or `rtl`, default
  `ltr`.
- `strings` is a flat object; keys are dot-separated segments, no empty
  segments. Values are non-empty strings.
- Placeholders use `{name}`. Every locale must use exactly the placeholder set
  of the English value for the same key.
- Plural groups use suffixes `.zero`, `.one`, `.two`, `.few`, `.many`,
  `.other`. A group is the set of keys sharing a base name across all
  catalogs; every locale must define every category returned by
  `new Intl.PluralRules(tag).resolvedOptions().pluralCategories` for that
  base. Example: `ru` needs `one`, `few`, `many`, `other`; `zh` needs
  `other`; `en` needs `one`, `other`. Category sets differ per language, so
  a group's keys are the union across catalogs, not the English subset.
  At render time an unexpected category falls back to `.other`.
- Keys not part of a plural group must not end in a plural suffix.

### 5.2 Generator

`tools/build-locales.mjs`:

- Reads and validates every `locale/*.json` in sorted order.
- Emits a deterministic region in `lib/client.js` between
  `/* @generated locales:begin */` and `/* @generated locales:end */`:

  ```js
  /* @generated locales:begin — run `node tools/build-locales.mjs` */
  const DICTIONARIES = {
    en: { "surface.title": "Artel", ... },
    ru: { ... },
    zh: { ... }
  };
  /* @generated locales:end */
  ```

  Strings are emitted with `JSON.stringify`, so quoting and escaping are
  always valid JavaScript. Key order follows the English catalog.
- Exports the validation and rendering functions so tests can call them.
- `node tools/build-locales.mjs --check` renders in memory, compares with the
  committed region, prints the first difference and exits non-zero when stale
  or invalid.
- Fails on: missing/extra non-plural keys relative to English, empty values,
  placeholder mismatch, missing or unexpected plural category, invalid `meta`,
  or a language id not matching the tag pattern. Duplicate keys are not
  detectable through `JSON.parse`, so they are covered by review and by the
  parity test's key count.
- Adding a language requires a new `locale/<tag>.json` and running the
  generator; the `available` list is derived from filenames at host boot.

### 5.3 Host event schema

Every host-produced user-visible record gains `key` and `params` while keeping
`text` as an English fallback:

```js
{
  kind: 'feed',
  key: 'feed.copy.preparing',
  params: { project: 'app' },
  text: 'Preparing a copy of app.'
}
```

The client resolves:

```js
function localized(record, t) {
  return record.key ? t(record.key, record.params) : record.text;
}
```

- `text` remains English so old clients, logs and external consumers keep
  working.
- Records persisted before this change have no `key` and render as before.
  No migration is performed.
- Server-computed values that are not free-form prose get the same treatment:
  queue progress (`lib/queue.js:226`), stop reasons (`:314-331`), branch
  labels (`:76`), task labels (`:104`), factory column labels
  (`lib/factory.js:78-96`).
- Raw payloads are never keyed: agent messages, tool output, diffs, file
  paths, commit hashes.

Key namespaces:

| Namespace   | Owner                                            |
| ----------- | ------------------------------------------------ |
| `feed.*`    | `lib/engine.js` status and log lines             |
| `queue.*`   | `lib/queue.js`, `lib/queue-runner.js`            |
| `factory.*` | `lib/factory.js`, `lib/factory-runner.js`        |
| `error.*`   | host error codes rendered by `describeError`     |
| existing UI | keys already in the 509-key catalog              |

### 5.4 Errors

`lib/routes.js:95` keeps `{ error, code }` and adds `params` when present:

```json
{ "error": "Issue #12 is not in review", "code": "factory/issue-not-in-review", "params": { "issue": 12 } }
```

The client maps `code` to `error.<code>`; unknown codes show the generic
`error.unknown` text with the HTTP status, not the raw Russian message. The
existing `factory/issue-*` and `artel/git-missing` mappings move into the same
table. `FactoryError` carries `code` and `params`; its `message` stays English
for logs and tests.

### 5.5 Settings storage and API

New module `lib/settings.js`:

- `readSettings(stateDir)` returns `{ version: 1, language: null }` when the
  file is absent or invalid.
- `writeSettings(stateDir, patch)` merges and writes atomically: temporary
  file in the same directory, then rename; the previous file is never
  truncated in place.
- `availableLocales(localeDir)` reads the directory, validates filenames, and
  returns `[{ id, nativeName }]` sorted with English first.
- `isValidLanguageTag(tag)` implements the pattern above.

Routes next to `/health` in `lib/routes.js`:

- `GET /api/dsh-artel/settings` →
  `{ language: "ru" | null, available: [{ id: "ru", nativeName: "Русский" }] }`.
- `POST /api/dsh-artel/settings` with `{ language: "ru" | null }` → same shape.
  `null` means "as in DSH". An unknown or malformed tag returns `400` with
  `code: "settings/invalid-language"`.
- Responses are not cached; the client fetches once per surface mount.

The *effective* language is computed on the client:
`language ?? localeOfDsh() ?? 'en'`, where `localeOfDsh()` returns the DSH
language tag when available, then `document.documentElement.lang`, then
`navigator.language`. An exact catalog match wins; otherwise the base language
is tried (`pt-BR` → `pt`); otherwise English.

### 5.6 Client language store and translator

A module-level store in `lib/client.js`:

```js
const languageStore = {
  chosen: null,        // persisted value
  effective: 'en',     // resolved tag
  available: [],       // from GET /settings
  t(key, params) {},
  setLanguage(tag) {}, // POST, then recompute and notify
  subscribe(listener) {}
};
```

- Fetched once when the surface mounts.
- `t(key, params)` resolves plural suffixes with
  `Intl.PluralRules(effective)` when a plural group exists, substitutes
  `{name}` placeholders, falls back to English, then to the key itself. In
  development it logs each missing key once.
- `translator(props)` returns `languageStore.t` instead of `props.t`, so all
  existing call sites keep working.
- DSH locale registration stays: DSH uses it for slots and the plugin card,
  but product strings never depend on DSH's active locale.
- Switching language calls `setLanguage`, updates `document.documentElement`
  `lang` on the surface root, and re-renders. No reload, no refetch of history.
- Another window picks up the change on its next mount or window focus; no
  realtime channel is added.

### 5.7 Switch UI

A globe menu in the surface header next to the close control:

- First item: "As in DSH" (`settings.language.auto`) showing the resolved tag.
- Then every available language under its `nativeName`.
- Selecting posts the setting and closes the menu; the current item is marked.
- The menu is keyboard reachable and uses the same popover pattern as the
  existing header menus.

### 5.8 Pluralization, formatting, direction

- Plural selection uses `Intl.PluralRules(effective)`; the hand-written rules
  at `lib/client.js:5580` are removed.
- Dates and times use `Intl.DateTimeFormat(effective, ...)` instead of
  `toLocaleString(undefined, ...)` at `lib/client.js:3674` and
  `lib/client.js:3854`. The browser time zone is kept.
- Numbers use `Intl.NumberFormat(effective)` where a number is formatted.
- `meta.dir` is read and applied as a `dir` attribute on the surface root, so
  a future RTL catalog renders without schema changes. Full RTL layout is out
  of scope.

## 6. Migration plan

### Phase 1 — foundation, no behavior change

1. Extend `locale/*.json` to the schema in 5.1, mechanically moving the 509
   keys from `lib/client.js` into `locale/en.json`, `locale/ru.json`,
   `locale/zh.json`. One commit, produced by the generator, no hand edits.
2. Add `tools/build-locales.mjs` and the generated region; replace the literal
   dictionaries.
3. Add `lib/settings.js`, the settings routes, and tests.
4. Add `languageStore`, `t()`, the header switch, and wire `translator()` to
   it.
5. Add `test/locales.test.js` and `test/settings.test.js`.

Exit criteria: the UI switches en/ru/zh instantly and identically to today;
all tests green; `--check` clean.

### Phase 2 — host keys by subsystem

Each subsystem converts its strings to `{ key, params, text }`, adds catalog
entries to all three languages, and updates its tests to assert keys and
parameters instead of prose.

1. **Queue** — `lib/queue.js:76`, `:104`, `:226`, `:314-331`;
   `lib/queue-runner.js:138-141`, `:415`, `:513`, `:549`, `:579`, `:620`,
   `:1256`, `:1359`. Smallest surface, visible result.
2. **Factory** — `lib/factory-runner.js:119-131`, `:320`, `:778`, `:810`,
   `:1205`, `:1843`; `lib/factory.js:78-96`, `:144`.
3. **Errors and routes** — `lib/routes.js:95` and the client error table.
4. **Engine feed** — `lib/engine.js:787` and the remaining status strings.
   Last because it has the most strings and the most test coverage.

Exit criteria: no Russian or hard-coded English prose reaches the client from
the host; every host test asserts keys.

### Phase 3 — polish and release

1. `Intl` pluralization and date/number formatting.
2. Documentation updates (section 7).
3. Version 0.14.0 and release checklist.

## 7. Testing

New and changed tests:

- `test/locales.test.js`: identical non-plural key sets, non-empty values,
  placeholder parity with English, exactly the plural categories each locale's
  `Intl.PluralRules` requires, valid `meta`, `nativeName` for every language,
  generated region matches the catalogs.
- `test/settings.test.js`: default when the file is absent, atomic write,
  merge semantics, `null` accepted, invalid tag rejected with `400`, available
  list derived from filenames.
- `test/client.test.js`: key takes precedence over `text`; legacy records
  without `key` render `text`; missing key falls back to English; plural
  selection for `ru` (`one`/`few`/`many`) and `zh` (`other`); switch posts the
  setting and re-renders.
- Host tests (`queue-runner`, `factory-runner`, `routes`): assert `key` and
  `params` rather than Russian prose; keep one test that `text` is English.
- `npm test` plus `node tools/build-locales.mjs --check` run in CI.

Manual smoke: install the tarball into a clean profile, switch each language,
open an existing run and ticket, confirm the feed, journal, progress and
errors all change.

## 9. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| 509-key move produces a large diff | Generated in one commit; `--check` proves the region is derived, not hand-edited. |
| Host tests pin Russian strings | Expected rewrite; land per subsystem with its tests. |
| DSH does not expose the active locale tag | Fallback chain `documentElement.lang` → `navigator.language` → `en`; exact/base/English matching. |
| Old persisted events stay in their write language | Accepted; no migration, `text` fallback keeps them readable. |
| Catalog drift after adding a language | CI `--check` and parity tests block the merge. |
| Windows atomic rename behavior | Same-directory temp file plus rename, with unlink-and-retry fallback. |

## 10. Acceptance criteria

- Switching en/ru/zh changes every visible product string, including already
  persisted runs, tickets, queue progress and errors.
- No Russian or English leakage remains in the product surface outside agent
  replies, command output, diffs and paths.
- A new language works by adding `locale/<tag>.json` and regenerating; host and
  client logic are untouched.
- `npm test` and `node tools/build-locales.mjs --check` pass; the packed
  tarball works in a clean profile.
